# Datasets

## How the data was made

All files are generated by `generate_datasets.py` with a fixed random seed (42).
Running the script again produces byte-identical files (checked with md5sum).
All data is fake. Emails use the reserved `example.com` domain.

To regenerate:

    python datasets/generate_datasets.py

## Baseline: planted problems

`orders_baseline.csv` has 200 rows: 190 clean orders plus 10 duplicates.
Problems were added on purpose, with exact counts:

| Problem | Count | Example |
|---|---|---|
| Exact duplicate rows | 10 | the same order appears twice |
| Messy names | 15 | `HENRY MARTIN `, `  noah smith` |
| Missing email | 10 | empty value |
| Invalid email | 5 | `n/a`, `unknown`, `missing@`, `noah.smith.example.com`, `@example.com` |
| Messy state | 12 | `vic`, `Victoria`, ` VIC ` |
| Zero or negative quantity | 8 | `0`, `-2` |
| Missing unit price | 6 | empty value |

Each problem is in a separate set of rows, so no row has two problems and every count is exact.
The exact order IDs for each problem are listed in `defects_summary.json`.

Two columns are kept clean on purpose, because they are used for the semantic drift tests:

- `order_date` is always `MM/DD/YYYY`. 118 of the 190 orders have a day above 12, which makes a day/month swap detectable.
- `unit_price` is always in dollars.

## Drifted files

Each drifted file is the baseline with one change, except the combined file, which has all four schema changes.

| File | Change |
|---|---|
| `orders_schema_drop_column.csv` | `email` column removed |
| `orders_schema_rename_column.csv` | `customer_name` renamed to `name` |
| `orders_schema_type_change.csv` | `quantity` becomes text, for example `3 units` |
| `orders_schema_add_column.csv` | new `discount_code` column at the end |
| `orders_schema_combined.csv` | all four changes above together |
| `orders_semantic_price_cents.csv` | `unit_price` in cents, for example `25545` instead of `255.45` |
| `orders_semantic_date_day_first.csv` | `order_date` becomes `DD/MM/YYYY` |

Every file is uploaded to S3 under the same name, `input/orders.csv`, so the pipeline sees the same file change between scheduled runs.

## Cleaning rules

The pipeline is asked to apply these rules:

1. Remove exact duplicate rows.
2. Trim spaces from `customer_name` and convert it to title case (`HENRY MARTIN ` becomes `Henry Martin`).
3. Standardise `state` to one of the 8 codes: NSW, VIC, QLD, WA, SA, TAS, ACT, NT. Trim spaces, use uppercase, and convert full names (`Victoria` becomes `VIC`).
4. Remove rows where `quantity` is 0 or below.
5. Remove rows where `unit_price` is missing.
6. Keep all remaining rows, but check each email. A valid email has text, one `@`, then a domain containing a dot. Replace invalid emails with an empty value, and add a column `email_valid` that is `true` for valid emails and `false` for missing or invalid ones.
7. Convert `order_date` to `YYYY-MM-DD` (`09/18/2026` becomes `2026-09-18`).
8. Add a column `line_total` = `quantity` × `unit_price`, rounded to 2 decimal places.

## Expected output for the baseline

- Rows: **176** (200 − 10 duplicates − 8 bad quantities − 6 missing prices)
- Columns: **9**: `order_id`, `customer_name`, `email`, `state`, `order_date`, `quantity`, `unit_price`, `line_total`, `email_valid`. Column order is not part of the rules.
- `email_valid`: **161** true and **15** false. The 15 false rows have an empty `email`.
- `state` contains only the 8 codes.
- No duplicate rows, no quantity of 0 or below, and no missing prices.

## Why these rules

Each drift test changes a column that at least one rule depends on, so a drift cannot pass through unnoticed just because nothing uses that column:

- Rename and drop affect rules 2 and 6.
- The type change affects rules 4 and 8.
- Prices in cents affect rule 8.
- Day-first dates affect rule 7.

The added `discount_code` column has no rule on purpose. It shows whether the pipeline passes an unknown column through, drops it, or fails.
